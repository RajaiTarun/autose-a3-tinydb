# ADR-002: Control flow is a plain Python state machine, not an LLM planner
**Status:** Accepted
**Date:** 2026-11-21

## Context
Stages must run in order, hand over only after a check passes, and go back (test→implement,
test→design, review→design/implement) within budgets. GitHub Actions jobs form an acyclic graph and cannot loop.

## Decision
We will run stages 1–5 inside **one `build` job** driven by `orchestrator.py`, a deterministic state machine.
**Code, not an agent, decides** every transition from check results. The Reviewer runs in its own job; a
review round starts a new run with `workflow_dispatch(issue, start_stage, round)`.

## Alternatives considered
- *An LLM planner choosing the next stage:* flexible, but unpredictable, hard to test, and it spends tokens on decisions code can make.
- *One Actions job per stage chained with `needs:`:* most visible in the UI, but no loops, and every hop has to upload and download artifacts.

## Consequences
- Positive: predictable, testable with stub agents at no cost, and budgets are enforced in one place.
- Negative: the go-back rules are fixed in code; an unusual failure cannot be "reasoned around".
- Review rounds cost one extra workflow run each, which is visible and linkable.

## Amendment (2026-11-24, found in the GitHub dry run)
The dry run (issue #4, PR #12) showed that the `ci.yml` run started by the release
stage passes on the PR head commit, but GitHub does not attach it to the PR, so the
required `ci-tests` check stays missing. GitHub also creates the PR's own
`pull_request` run but holds it ("action_required") until a person approves it.
After that approval, `ci-tests` showed on the PR and it became mergeable.
Decision: keep the dispatched run as the stage 5 check (automatic, on the exact
commit), and have the release stage comment on the PR that a person must click
*Approve workflows to run*. That click is the human merge gate; AutoSE never merges.
